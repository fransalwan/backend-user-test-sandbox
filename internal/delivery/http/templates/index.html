💰 Modul L1 • Hukum Zero-Tolerance Moneter IEEE 754 vs int64

Mengapa Dilarang Keras Menggunakan Float/Double untuk Uang?

Standar IEEE 754 menggunakan aproksimasi biner (basis 2) yang tidak mampu merepresentasikan pecahan desimal basis 10 (seperti 0.1 atau 0.2) secara presisi mutlak. Akibatnya timbul celah pembulatan (contoh: 0.1 + 0.2 = 0.30000000000000004).

❌ Cara Salah (Float):
var saldo float64 = 100.00
saldo -= 0.10 // berisiko rounding error akumulatif
✅ Standar Industri (int64 sen):
var saldoCents int64 = 10000 // $100.00
saldoCents -= 10 // persis 10 sen ($0.10), zero float!
🔒 Modul L2 • Anatomi Race Condition & Lost Update Critical Section

Apa yang Terjadi Saat 50 Goroutine Menarik Saldo Bersamaan?

Ketika dua atau lebih thread mengeksekusi siklus Read-Modify-Write (RMW) pada waktu bersamaan tanpa penguncian, terjadi fenomena Lost Update:

// Skenario Bencana Lost Update (Saldo Awal: $100):
Goroutine A: Baca saldo = $100 → Hitung (100 - 50 = $50)
Goroutine B: Baca saldo = $100 → Hitung (100 - 50 = $50) [BACAAN BASI / STALE!]
Goroutine A: Tulis saldo = $50
Goroutine B: Tulis saldo = $50 → Menimpa tulisan A! (Saldo akhir $50, nasabah tarik $100 tapi hanya berkurang $50!)
⚙️ Modul L3 • Primitive Sinkronisasi Go: Kapan Pakai Apa? Mutex vs Atomic
Primitive Mekanisme Kapan Digunakan Catatan Kritis
sync.Mutex Exclusive Mutual Exclusion Lock Operasi multi-step (cek saldo → kurangi → catat ledger) Wajib defer mu.Unlock()
sync.RWMutex Multiple Readers, Single Writer Read-heavy data (sering cek saldo, jarang mutasi) Writer lock memblokir semua reader
sync/atomic Instruksi hardware CPU (CAS) Counter sederhana tanpa logika percabangan Tanpa context switch, ultra-cepat

🛡️ Modul S1 • Mengapa Disable Button di Frontend Tidak Cukup? API Idempotency

Anomali Timeout Jaringan & Retry Otomatis

Di dunia nyata, request HTTP transfer uang bisa sukses didebit di database, tetapi koneksi putus saat mengirim respons balik ke aplikasi mobile nasabah. Aplikasi mobile yang timeout akan secara otomatis me-retry request kedua.

⚠️ Mengapa Hanya Frontend Disable Tombol Itu Berbahaya:

Tombol disable di UI hanya mencegah double-click manusia. Tombol itu tidak bisa mencegah retry otomatis oleh SDK jaringan seluler, tidak bisa mencegah refresh browser, dan tidak bisa mencegah skrip API penyerang. Backend wajib mengimplementasikan perlindungan idempotensi mandiri!

🗺️ Modul S2 • State Machine Alur Idempotensi di Backend State Lifecycle
1. Kunci Baru Masuk Status: PROCESSING

Kunci disimpan dengan atomic lock (Redis SETNX / DB UNIQUE). Transaksi dijalankan.

2. Request Konkuren Tolak: HTTP 409 Conflict

Jika request kedua datang saat request pertama masih berstatus PROCESSING, cegat segera!

3. Transaksi Tuntas Replay: HTTP 200 OK

Saat status COMPLETED, retry berikutnya langsung menyajikan cached response tanpa mutasi ulang.

💥 Modul S3 • Dual-Write Hazard: Jangan Panggil Bank di Dalam SQL Tx! Anti-Pattern

Mengapa Panggilan HTTP Eksternal di Dalam Transaksi SQL Berbahaya?

Membuka transaksi database (BEGIN ... COMMIT) lalu melakukan panggilan jaringan lambat (http.Post ke Bank mitra) adalah anti-pattern fatal:

  • Database Connection Starvation: Koneksi database tersandera berdetik-detik menunggu respons bank, membuat seluruh pool koneksi penuh dan server crash (HTTP 500).
  • Dual-Write Inconsistency: Jika bank sukses mentransfer dana tetapi setelah itu server mati sebelum tx.Commit() berhasil, transaksi database otomatis ROLLBACK. Uang bank sudah keluar, tetapi saldo lokal nasabah tidak berkurang!
Lab Uji Koding Manual 2 • System Design Preparation

Tantangan: Implementasikan State Machine Idempotency Engine

Petunjuk State Machine: Periksa kunci di e.records[key]. Jika belum ada, set nilainya ke "PROCESSING" dan kembalikan false, nil. Jika nilainya "PROCESSING", tolak dengan false, ErrInFlightConflict. Jika "COMPLETED", kembalikan true, nil (Replay).
e.mu.Lock()
defer e.mu.Unlock()
if key == "" { return false, ErrMissingKey }
status, exists := e.records[key]
if exists && status == "PROCESSING" { return false, ErrInFlightConflict }
if exists && status == "COMPLETED" { return true, nil }
e.records[key] = "PROCESSING"
return false, nil
