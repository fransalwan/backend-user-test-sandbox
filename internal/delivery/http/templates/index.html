💻 Tahap 1: Live Coding • Financial Transaction Deduplication (Sliding Window)

Pewawancara (Staff Software Engineer): "Di platform payment gateway, gangguan sinyal seluler atau retry agresif sering mengirimkan transaksi kembar. Diberikan slice data Transaction dan windowSeconds (misal 60 detik). Tuliskan fungsi Go efisien untuk mendeteksi dan mengembalikan ID dari transaksi duplikat (UserID dan Amount persis sama dalam selang waktu ≤ windowSeconds)!"

🧪 Contoh Kasus Uji (Test Cases) 3 Examples
Example 1: Duplikat Terdeteksi Valid Duplicate
txs: [ID:"tx_01", User:"alice", Amt:50k, t:100], [ID:"tx_02", User:"alice", Amt:50k, t:120]
windowSeconds: 60
Output: ["tx_02"]
Penjelasan: User dan nominal sama, selisih 20 detik ≤ 60s (Duplikat).
Example 2: Nominal / User Berbeda No Duplicate
txs: [ID:"tx_01", User:"alice", Amt:50k, t:100], [ID:"tx_02", User:"alice", Amt:75k, t:115]
windowSeconds: 60
Output: []
Penjelasan: Nominal berbeda (50k vs 75k), bukan transaksi kembar.
Example 3: Jeda Melebihi Window Normal Recurring
txs: [ID:"tx_01", User:"alice", Amt:50k, t:100], [ID:"tx_02", User:"alice", Amt:50k, t:250]
windowSeconds: 60
Output: []
Penjelasan: Selisih 150 detik > 60s window, transaksi berulang sah.
📋 Constraints & Spek Industri: Wajib O(N)
  • 1 ≤ len(txs) ≤ 10⁴
  • Amount > 0 (satuan sen int64)
  • windowSeconds > 0 (biasanya 30s s/d 120s)
  • Wajib O(N) Time Complexity via Hash Map.
  • Solusi nested loop O(N²) akan ditolak komite karena TLE!
Butuh Bantuan?
💡 Hint 1: Hash Map Composite Key

Dua transaksi dianggap sama jika UserID dan Amount identik. Buat string key gabungan, misal: key := tx.UserID + "_" + strconv.FormatInt(tx.Amount, 10) atau fmt.Sprintf("%s_%d", tx.UserID, tx.Amount).

💡 Hint 2: Melacak Timestamp Terakhir

Simpan timestamp terakhir per key dalam seen := make(map[string]int64). Jika key sudah ada di map dan tx.Timestamp - lastTime ≤ windowSeconds, tambahkan tx.ID ke slice hasil duplikat!

💡 Hint 3: Kerangka Algoritma
var duplicates []string
seen := make(map[string]int64)
for _, tx := range txs {
  key := fmt.Sprintf("%s_%d", tx.UserID, tx.Amount)
  if prev, ok := seen[key]; ok && (tx.Timestamp - prev ≤ windowSeconds) {
    duplicates = append(duplicates, tx.ID)
  }
  seen[key] = tx.Timestamp
}

🔥 Production War Room: Flash Sale & Concurrency Defense

Pewawancara (Engineering Manager): Uji mitigasi kegagalan sistem pada beban puncak! Gunakan pembatasan laju (Rate Limiting) untuk melindungi pool database dari thundering herd saat 250 request serentak berebut voucher.

🛡️ Skenario Mitigasi Insiden: Thundering Herd & Rate Limiting:

Bayangkan kapasitas pemrosesan backend dibatasi 40 request per detik. Jika 250 request merangsek masuk bersamaan tanpa proteksi, database pool akan kehabisan koneksi (HTTP 500) dan kuota voucher bisa minus (overselling). Aktifkan Token Bucket Rate Limiting (Maks 40 RPS) → Amati 50 kuota terserap tepat habis (0) dan kelebihan request ditolak rapi dengan HTTP 429 Too Many Requests untuk menuntaskan evaluasi dan menerbitkan Surat Penawaran Kerja (Offer Letter)!

💼 5 Pertanyaan Wawancara Teknis Paling Sering Diuji (Junior Backend):

1. Mengapa nilai uang TIDAK BOLEH disimpan sebagai Float / Double?

Representasi IEEE-754 floating point memiliki ketidakpresisian biner (misal: 0.1 + 0.2 = 0.30000000000000004). Di sistem finansial, selalu gunakan int64 dalam satuan sen / terkecil atau tipe NUMERIC(18, 4) di database.

2. Apa perbedaan Row-Level Lock (SELECT FOR UPDATE) vs Optimistic Lock?

Pessimistic (SELECT FOR UPDATE) mengunci baris database secara eksklusif selama transaksi aktif, cocok saat konflik sangat tinggi (misal: penarikan saldo dompet). Optimistic Lock (kolom version) memeriksa apakah version berubah saat UPDATE, cocok saat transaksi jarang bertabrakan.

3. Bagaimana siklus Idempotency Key menangani status duplikat?

Jika request pertama masih dalam status PROCESSING dan request kedua masuk dengan kunci sama, kembalikan HTTP 409 Conflict. Jika request pertama sudah COMPLETED namun request kedua mengirim parameter berbeda, kembalikan HTTP 422 Unprocessable Entity.

4. Mengapa Go menggunakan explicit error handling (if err != nil) daripada try-catch?

Error di Go diperlakukan sebagai nilai biasa (first-class values). Ini memaksa developer secara eksplisit menangani setiap skenario kegagalan tanpa menyembunyikan alur kontrol program di dalam exception block tak terduga.

5. Apa pembagian tanggung jawab Clean Architecture (Handler vs Service vs Repository)?

Handler: Parsing HTTP request, validasi format, serialisasi response. Service/Usecase: Aturan bisnis inti, orkestrasi transaksi. Repository: Abstraksi query database / persistence tanpa mencampur logika bisnis.
