💰 Modul 0 • Hukum Utama Rekayasa Finansial Zero-Tolerance Rule

1. Mengapa Dilarang Keras Menggunakan Float/Double untuk Uang?

Format bilangan floating-point (standar IEEE 754) menggunakan aproksimasi biner base-2 yang tidak bisa merepresentasikan pecahan desimal basis 10 secara presisi.

// Contoh Bug Akurasi Float di Go:
var a float64 = 0.1
var b float64 = 0.2
fmt.Println(a + b) // Hasil: 0.30000000000000004 (Bocor 0.0000000000000004!)
✅ Standar Industri Perbankan & Fintech: Simpan nilai moneter dalam satuan terkecil (sen / cents) sebagai int64 di Go dan BIGINT di SQL. Contoh: $1.000,00 direpresentasikan murni sebagai angka bulat 100000 sen.

2. Prinsip Double-Entry Bookkeeping (Pembukuan Berpasangan)

Jangan pernah hanya mengupdate saldo secara naif (UPDATE wallets SET balance = balance - 100). Tanpa riwayat mutasi, sistem gagal lolos audit keuangan. Di sistem enterprise, saldo adalah akumulasi (sum) dari seluruh baris mutasi di tabel ledger_entries:

  • Immutable (Append-Only): Baris ledger dilarang di-UPDATE atau di-DELETE.
  • Zero-Sum Balance: Setiap pengeluaran (DEBIT) harus seimbang dengan penerimaan (CREDIT) di sisi lawan (misal rekening tujuan atau akun kas penampung).
🔒 Modul 1 • Concurrency & Locking Strategies Ujian Tahap 1

Anatomi Bencana: Lost Update & Overdraft Race Condition

Bayangkan saldo Alice tersisa $25. Dua goroutine berjalan konkuren dan masing-masing mencoba menarik $25:

Goroutine A: Baca saldo ($25) ≥ $25 → VALID (lanjut proses)
Goroutine B: Baca saldo ($25) ≥ $25 → VALID (karena A belum selesai tulis!)
Goroutine A: Potong $25 → Tulis saldo $0
Goroutine B: Potong $25 → Tulis saldo -$25 (OVERDRAFT / SALDO MINUS!)

Komparasi Solusi Penguncian:

Pessimistic Locking SELECT FOR UPDATE

Mengunci baris DB eksklusif. Transaksi lain antre menunggu commit. Cocok untuk transaksi berfrekuensi tulis tinggi (hot wallet).

Optimistic (CAS) WHERE version = ?

Tanpa lock di awal. Cek nomor versi saat update. Jika versi sudah berubah, retry. Cocok untuk sistem read-heavy / low-contention.

Redis Lock SET key val NX PX TTL

Lock terdistribusi di memori sebelum menyentuh DB RDBMS. Melindungi cluster microservice independen.

🛡️ Modul 2 • Idempotency Engine & Anti Double-Spending Ujian Tahap 2

Anatomi Bencana: Badai Retry Jaringan (Network Retry Storm)

Sinyal koneksi internet mobile tidak pernah 100% andal. Ketika klien mengirim instruksi transfer $50, server sukses mendebet saldo. Namun sebelum HTTP 200 tiba di HP nasabah, koneksi terputus (*timeout*). Klien otomatis me-retry 5 kali. Tanpa idempotensi, nasabah terdebet $250!

4 Pilar Engine Idempotensi Standar Stripe:

1.
Idempotency-Key (UUIDv4): Dikirim oleh klien via HTTP header unik per transaksi bisnis.
2.
Payload Hashing (SHA-256): Hash dari method, path, dan JSON request body. Jika key sama dipakai dengan nominal berbeda (tampering), tolak dengan HTTP 422 Unprocessable Entity.
3.
In-Flight Distributed Lock: Saat transaksi pertama sedang berjalan (IN_PROGRESS), request duplikat konkuren langsung dicegat dengan HTTP 409 Conflict.
4.
Response Caching (COMPLETED): Setelah transaksi pertama sukses, respons disimpan. Retry berikutnya menerima respons tersimpan seketika tanpa memotong saldo ulang!
🔄 Modul 3 • Distributed Saga & Transactional Outbox Ujian Tahap 3

Anatomi Bencana: The Dual-Write Hazard

Ketika nasabah menarik dana ke rekening Bank BCA, aplikasi harus melakukan 2 hal: (1) potong saldo database lokal, dan (2) panggil API HTTP Bank BCA.

⚠️ Mengapa Dilarang Memanggil API Luar di dalam SQL Transaction? Jika pemanggilan API Bank ditaruh di dalam BEGIN ... COMMIT, DB connection pool tersandera menunggu latensi jaringan pihak ketiga. Dan jika bank sukses mentransfer uang tapi server lokal crash sebelum Commit, uang kas bank keluar namun saldo dompet di aplikasi tidak berkurang (Kebocoran Finansial Fatal!).

Arsitektur Solusi: Outbox Pattern & Saga Compensation

  • 1. Transactional Outbox: Simpan perubahan saldo dan catatan event ke tabel outbox_events dalam SATU transaksi ACID lokal. Background relay worker membaca outbox secara asinkron dan mengirim pesan dengan jaminan At-Least-Once Delivery.
  • 2. Compensating Transaction (Auto-Refund): Jika API Bank mitra mengembalikan HTTP 500 atau 504 Timeout, Saga Orchestrator secara otomatis memicu transaksi penyeimbang: mengkreditkan kembali saldo nasabah dan mencatat REFUND_DISBURSEMENT_FAILED di audit ledger.
⚡ Modul 4 • High Traffic & Flash Sale Isolation Ujian Tahap 4

Anatomi Bencana: The Thundering Herd & Overselling

Saat Flash Sale diskon 99% dibuka tengah malam, 10.000 user menekan tombol serentak memperebutkan 50 voucher. Jika semua request menembus database SQL:

  • Connection pool database habis seketika (max_connections reached).
  • Race condition menyebabkan stok voucher terjual melebihi kuota (Overselling).

Arsitektur Pertahanan 3 Lapis (Defense-in-Depth):

Lapis 1: Token Bucket

Rate limiter membatasi burst (misal 50 req) dan menolak kelebihan traffic di pintu masuk dengan HTTP 429 Too Many Requests.

Lapis 2: Redis DECRBY

Stok dipotong atomic di memory dalam 0.5 ms. Jika hasil < 0, tolak seketika tanpa query RDBMS sedikitpun!

Lapis 3: Worker Queue

Hanya kuota yang sukses merebut slot di Redis yang dialirkan ke antrean worker untuk ditulis ke PostgreSQL secara bertahap.

💡 Modul 5 • Tanya Jawab Wawancara Level Principal Interview Cheatsheet
Q1: Kapan memilih Pessimistic Locking dibanding Optimistic Locking?

Jawaban Senior: Pilih Pessimistic Lock ketika konflik tulis sangat sering terjadi pada satu entitas (seperti hot wallet saldo terbatas). Jika memakai optimistic CAS di hot wallet, puluhan goroutine akan terus-menerus gagal versi dan boros CPU melakukan retry. Sebaliknya, pilih Optimistic Lock jika sistem bersifat read-heavy dengan tingkat konflik rendah (misal pembaruan profil user atau katalog belanja).

Q2: Bagaimana menjamin Exactly-Once Semantics saat mengirim pembayaran?

Jawaban Senior: Secara fisik jaringan (Two-Generals Problem), Exactly-Once murni pada layer transport adalah mustahil karena koneksi bisa putus kapan saja. Di fintech, Exactly-Once dijamin melalui kombinasi At-Least-Once Delivery (menggunakan Transactional Outbox + Message Broker retries) digabungkan dengan Idempotent Consumer (tabel idempotensi & deduplication key) di sisi penerima.

Q3: Bagaimana jika node Redis yang memegang distributed lock mati?

Jawaban Senior: Gunakan TTL otomatis pada key lock agar tidak terjadi permanent deadlock, terapkan Watchdog heartbeat untuk memperpanjang lock selama pemrosesan aktif, dan wajib sertakan Fencing Token (nomor versi inkremental yang divalidasi di database) sehingga jika lock lama kedaluwarsa sebelum pekerja selesai, transaksi lamanya akan ditolak oleh DB.

💻 Live Coding: Safe Concurrent Hot-Wallet Deduct

Implementasikan method pemotongan saldo dompet yang thread-safe di bawah serbuan 50 goroutine tanpa overdraft saldo (Invarian Saldo ≥ $0).

📋 Constraints & Spesifikasi Ujian: Ketik kode manual • Tanpa contekan instan
  • amount > 0 (nominal penarikan dalam sen / int64)
  • wallet.balance >= 0 (Invarian Moneter: DILARANG MINUS / OVERDRAFT!)
  • Wajib mengembalikan ErrInsufficientFunds jika saldo tidak mencukupi.
  • Uji Stres (Test Case 3): 50 goroutine menarik $25 serentak dari saldo $1.000 → Saldo akhir tepat $0.
Butuh Bantuan?
💡 Hint 1: Memahami Masalah Race Condition (Lost Update)

Operasi pengecekan saldo if w.balance < amount dan pemotongan saldo w.balance -= amount adalah dua langkah terpisah. Jika 50 goroutine membaca saldo pada detik yang sama, semuanya akan melihat saldo mencukupi dan semuanya akan memotong saldo! Anda harus memastikan hanya satu goroutine yang boleh membaca dan memotong saldo pada satu waktu.

💡 Hint 2: Menambahkan Pengunci Mutex ke Struct

Go menyediakan primitif sinkronisasi memori bawaan yaitu sync.Mutex. Tambahkan field mu sync.Mutex ke dalam deklarasi type SharedWallet struct agar dompet memiliki kunci pengaman sendiri.

💡 Hint 3: Pola Penulisan Lock & Defer Unlock

Di awal fungsi DeductWallet, ketik w.mu.Lock(). Tepat di baris berikutnya, ketik defer w.mu.Unlock(). Menggunakan defer menjamin lock akan selalu dilepaskan meskipun fungsi Anda me-return error ErrInsufficientFunds di tengah jalan!
