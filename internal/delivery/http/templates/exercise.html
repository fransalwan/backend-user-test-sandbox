Fungsi menghitung biaya transfer dan PPN 11% menggunakan perkalian pecahan biner IEEE-754. Pada jutaan transaksi, pecahan 0.00000000000004 menumpuk menjadi selisih saldo nyata yang gagal dalam audit Bank Indonesia.

Tugas Debugging: Hapus konversi ke float64! Hitung fee sebagai (amountCents * 25) / 1000 dan PPN sebagai (feeCents * 11) / 100 murni dengan integer math.

🔍 Hint 1: Clue Konseptual ▼
Hindari semua konversi ke float64. Pecahan biner IEEE-754 menghasilkan rounding error tak terduga. Operasi moneter fintech wajib diselesaikan dalam basis terkecil (sen/cents) dengan integer math murni.

feeCents = (amountCents * 25) / 1000

totalDeduction = feeCents + taxCents
return feeCents, taxCents, totalDeduction
🔑 Hint 3: Solusi Standar Tech Lead + Penjelasan ▼ 
func CalculateTransactionFee(amountCents int64, feePercent float64) (feeCents int64, taxCents int64, totalDeduction int64) {
    // 2.5% fee = 25 / 1000
    feeCents = (amountCents * 25) / 1000
    // 11% PPN tax dari fee
    taxCents = (feeCents * 11) / 100
    totalDeduction = feeCents + taxCents
    return feeCents, taxCents, totalDeduction
}

💡 Tech Lead Note: Selalu terapkan integer arithmetic untuk ledger moneter. Pembulatan integer division di Go konsisten dan mencegah selisih pecahan yang dapat merugikan perusahaan saat rekonsiliasi jutaan transaksi.

Kurikulum Fase 1 • Go-Routines & Channel, Buffer, & Mutex Fase 1: Concurrency Basics

Skenario: Penarikan Serentak (Race Hazard) Mengakibatkan Saldo Overdraft

Dua transaksi penarikan saldo $10 dieksekusi bersamaan di dua goroutine berbeda pada akun bersaldo $15. Karena struct tidak memiliki synchronization primitive, kedua goroutine membaca saldo $15 secara serentak, menyetujui penarikan, dan menyebabkan saldo akhir minus $-5.

Tugas Debugging: Tambahkan mu sync.Mutex di dalam struct HotWallet, dan gunakan w.mu.Lock() dan defer w.mu.Unlock() di fungsi Withdraw.

💡 Sistem Bantuan Berjenjang (3-Tier Hints) Buka bertahap jika buntu
🔍 Hint 1: Clue Konseptual ▼
Operasi pengecekan saldo (w.Balance >= amount) dan pengurangan saldo (w.Balance -= amount) adalah operasi multi-langkah di memori. Tanpa mutual exclusion lock, goroutine lain dapat menyusup di antara langkah tersebut (Time-of-Check to Time-of-Use bug).
🧩 Hint 2: Pseudocode / Kerangka Logika ▼ 
type HotWallet struct {
    mu sync.Mutex
    Balance int64
}

func (w *HotWallet) Withdraw(amount int64) bool {
    w.mu.Lock()
    defer w.mu.Unlock()
    // cek saldo dan kurangi...
}
🔑 Hint 3: Solusi Standar Tech Lead + Penjelasan ▼ 
type HotWallet struct {
    mu      sync.Mutex
    Balance int64
}

func (w *HotWallet) Withdraw(amount int64) bool {
    w.mu.Lock()
    defer w.mu.Unlock()

    if w.Balance >= amount {
        w.Balance -= amount
        return true
    }
    return false
}

💡 Tech Lead Note: Selalu posisikan defer w.mu.Unlock() tepat setelah pemanggilan Lock() untuk mencegah *mutex leak* atau kebuntuan (deadlock) jika terjadi branching logika atau panic.

Kurikulum Fase 2 • Concurrency Pattern di Go Fase 2: Concurrency & Timeout

Skenario: Background Poller Berjalan Tanpa Henti Saat HTTP Client Disconnect

Fungsi polling memeriksa status settlement bank setiap 500ms dalam infinite loop. Jika nasabah menutup browser atau context timeout (3 detik), loop ini tidak pernah berhenti karena tidak mendengarkan ctx.Done(). Ribuan goroutine liar menumpuk dan memakan CPU server!

Tugas Debugging: Di dalam loop, gunakan konstruksi select { case <-ctx.Done(): return ctx.Err(); case <-ticker.C: ... } untuk segera keluar begitu context selesai.
⏱️ Interactive Visualizer: Context Lifecycle Radar Simulasi interaktif
Klik salah satu tombol simulasi untuk melihat sinyal pembatalan context...
💡 Sistem Bantuan Berjenjang (3-Tier Hints) Buka bertahap jika buntu
🔍 Hint 1: Clue Konseptual ▼
Loop tidak boleh memblokir sepihak hanya pada saluran ticker (<-ticker.C). Gunakan statement select untuk mendengarkan dua event serentak: sinyal pembatalan / timeout dari context, atau ketukan interval ticker berikutnya.
🧩 Hint 2: Pseudocode / Kerangka Logika ▼ 
for {
    select {
    case <-ctx.Done():
        return ctx.Err()
    case <-ticker.C:
        if checkBankStatus() {
            return nil
        }
    }
}
🔑 Hint 3: Solusi Standar Tech Lead + Penjelasan ▼ 
func PollPaymentSettlement(ctx context.Context, checkBankStatus func() bool) error {
    ticker := time.NewTicker(500 * time.Millisecond)
    defer ticker.Stop()

    for {
        select {
        case <-ctx.Done():
            return ctx.Err()
        case <-ticker.C:
            if checkBankStatus() {
                return nil
            }
        }
    }
}

💡 Tech Lead Note: Jangan lupa defer ticker.Stop() untuk melepas resource timer runtime Go, dan selalu return ctx.Err() saat context dibatalkan agar caller mengetahui penyebab spesifik (Canceled vs DeadlineExceeded).

Kurikulum Fase 2 • Web Server dan Go Routing (API Security) Fase 2: REST Idempotency

Skenario: Double Spending Terjadi Saat Request Paralel Masuk dengan Key Sama

Fungsi verifikasi idempotency hanya mengecek apakah status sudah COMPLETED. Ketika klien menekan tombol bayar 2x secara sangat cepat (paralel), request kedua masuk saat request pertama masih dalam status PROCESSING. Handler meloloskan keduanya dan saldo terpotong 2 kali!

Tugas Debugging: Jika status == "PROCESSING", segera kembalikan false, ErrInFlightConflict agar request kedua dicegat dengan HTTP 409 Conflict.
🔄 Interactive Visualizer: Idempotency In-Flight State Simulasi interaktif
Klik salah satu tombol simulasi untuk melihat status machine idempotency...
💡 Sistem Bantuan Berjenjang (3-Tier Hints) Buka bertahap jika buntu
🔍 Hint 1: Clue Konseptual ▼
Idempotency membedakan status PROCESSING (transaksi sedang berjalan di worker lain) dan COMPLETED (transaksi sudah tuntas). Request konkuren dengan key yang sama saat in-flight wajib ditolak dengan status konflik (HTTP 409).
🧩 Hint 2: Pseudocode / Kerangka Logika ▼ 
if exists {
    if status == "PROCESSING" {
        return false, ErrInFlightConflict
    }
    if status == "COMPLETED" {
        return false, ErrSuccessReplay
    }
}
m.store[key] = "PROCESSING"
return true, nil
🔑 Hint 3: Solusi Standar Tech Lead + Penjelasan ▼ 
func (m *IdempotencyManager) AcquireOrReplay(key string) (bool, error) {
    m.mu.Lock()
    defer m.mu.Unlock()

    status, exists := m.store[key]
    if exists {
        if status == "PROCESSING" {
            return false, ErrInFlightConflict
        }
        if status == "COMPLETED" {
            return false, ErrSuccessReplay
        }
    }

    m.store[key] = "PROCESSING"
    return true, nil
}

💡 Tech Lead Note: Jangan lupa melakukan lock map sebelum membaca dan menulis. Pola status transisi State Machine (NEW → PROCESSING → COMPLETED / FAILED) adalah standar industri fintech mencegah race condition tingkat API gateway.

Kurikulum Fase 3 • Database NoSQL (Redis) & Caching Strategy Fase 3: NoSQL Cache-Aside

Skenario: Cache Miss Gagal Mengambil Data Database & Thundering Herd

Fungsi GetProductDetail membaca dari NoSQL Redis cache. Ketika terjadi Cache Miss (data belum di-cache atau expired), fungsi langsung melempar error daripada memanggil database fallback (dbQueryFallback) dan menyimpan kembali hasilnya ke cache. Akibatnya klien mendadak gagal transaksi!

Tugas Debugging: Jika data tidak ada di cache: 1) Panggil dbData := dbQueryFallback(productID), 2) Simpan ke m.cacheStore[productID] = dbData, 3) Kembalikan dbData, nil!
⚡ Interactive Visualizer: Cache-Aside Flowchart Simulasi interaktif
Klik salah satu tombol simulasi untuk melihat alur Cache Hit vs Miss...
💡 Sistem Bantuan Berjenjang (3-Tier Hints) Buka bertahap jika buntu
🔍 Hint 1: Clue Konseptual ▼
Pola Cache-Aside mengasumsikan Cache adalah pembantu, bukan sumber kebenaran tunggal (single source of truth). Jika data nihil di cache (Cache Miss), aplikasi harus memuat data dari database utama, menuliskan hasilnya kembali ke cache untuk request berikutnya, lalu mengembalikannya ke klien.
🧩 Hint 2: Pseudocode / Kerangka Logika ▼ 
data, found := m.cacheStore[productID]
if found {
    return data, nil
}
dbData := dbQueryFallback(productID)
m.cacheStore[productID] = dbData
return dbData, nil
🔑 Hint 3: Solusi Standar Tech Lead + Penjelasan ▼ 
func (m *ProductCacheManager) GetProductDetail(ctx context.Context, productID string, dbQueryFallback func(string) string) (string, error) {
    data, found := m.cacheStore[productID]
    if found {
        return data, nil
    }

    // Cache Miss -> Ambil dari Database & Update Cache
    dbData := dbQueryFallback(productID)
    m.cacheStore[productID] = dbData
    return dbData, nil
}

💡 Tech Lead Note: Cache-Aside adalah pola paling umum untuk read-heavy workload di backend skala besar. Dalam produksi, penulisan ke cache disertai dengan TTL (Time To Live, misal 5 menit) untuk menjaga sinkronisasi data dengan database.
