🗣️ 1. Think Out Loud

Jangan diam membisu saat melihat kode rusak. Ucapkan apa yang Anda amati: "Saya melihat di baris ini fungsi menggunakan float64 untuk uang..."

🔍 2. Reproduce Bug First

🎯 3. Isolate The Root Cause

Bedakan antara gejala (*symptom*) dan akar masalah (*root cause*). Ubah kode secara terarah, bukan menebak-nebak acak.

🛠️ Modul Latihan 1: Live Debugging Drills (Repetisi Kasus Nyata)

Pilih skenario kasus di bawah, temukan cacat logika pada kode, ketik perbaikannya di editor, dan verifikasi!

Kasus 1 • Financial Calculation Accuracy Level: Junior Fundamental

Skenario: Fee & PPN Transaksi Mengalami Pembulatan Bocor (Float Precision Leak)

Fungsi di bawah digunakan untuk menghitung biaya admin transaksi (2.5%) dan PPN (11%). Namun fungsi ini ditulis menggunakan tipe float64. Pada 1.000 transaksi mikro, audit pembukuan menemukan selisih Rp 12,40 yang hilang akibat representasi biner IEEE-754.

Tugas Debugging: Ubah kalkulasi agar murni menggunakan integer math (int64). Biaya admin 2.5% dihitung sebagai (amountCents * 25) / 1000 atau (amountCents * 250) / 10000 dan PPN 11% dihitung dari fee tersebut.
Tersimpan di browser
Uji 3 skenario nominal: Rp 10.000, Rp 50.000, Rp 125.750
Kasus 2 • Concurrency Safety & Data Race Level: Junior Fundamental

Skenario: Saldo Dompet Minus Karena Eksekusi Penarikan Bersamaan Tanpa Mutex

Fungsi Withdraw membaca nilai w.Balance dan langsung memotongnya tanpa sinkronisasi goroutine. Saat 20 goroutine mengeksekusi penarikan $10 serentak pada dompet yang hanya bersaldo $15, saldo akhir berakhir negatif (overdraft) karena race hazard.

Tugas Debugging: Tambahkan sync.Mutex pada struct HotWallet, lalu gunakan w.mu.Lock() dan w.mu.Unlock() (atau defer w.mu.Unlock()) agar operasi periksa-dan-potong menjadi atomik!
Tersimpan di browser
Uji simulasi 20 concurrent goroutines • Go -race detector
Kasus 3 • API Idempotency State Machine Level: Intermediate Core

Skenario: Dua Request Serentak Lolos Bersamaan Karena Status PROCESSING Tidak Terdeteksi

Klien mengirim request transfer, lalu karena koneksi sedikit lambat, aplikasi me-retry request kedua pada milidetik ke-50 saat request pertama masih berjalan. Fungsi AcquireOrReplay hanya mengecek status COMPLETED, sehingga request kedua tidak dianggap sebagai konflik, melainkan ikut diproses!

Tugas Debugging: Jika key sudah ada di store dan statusnya adalah "PROCESSING", fungsi wajib mengembalikan false, ErrInFlightConflict agar handler dapat merespons klien dengan HTTP 409 Conflict!
Tersimpan di browser
Uji state: In-Flight Concurrency vs Completed Replay
Kasus 4 • Resource Management & Goroutine Leak Level: Intermediate Core

Skenario: Background Poller Berjalan Terus Menerus Saat HTTP Client Sudah Disconnect

Fungsi polling memeriksa status settlement bank setiap 500ms dalam infinite loop. Jika nasabah menutup browser atau context timeout (3 detik), loop ini tidak pernah berhenti karena tidak mendengarkan ctx.Done(). Ribuan goroutine liar menumpuk dan memakan CPU server!

Tugas Debugging: Di dalam loop, gunakan konstruksi select { case <-ctx.Done(): return ctx.Err(); case <-ticker.C: ... } untuk segera keluar begitu context selesai.
Tersimpan di browser
Uji pembatalan context • Deteksi zero goroutine leak
