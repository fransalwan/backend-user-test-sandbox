⚡ Modul L1 • Analisis Kompleksitas Algoritma (Big-O Notation) O(1) vs O(N) vs O(N²)

Mengapa Solusi O(N²) Brute Force Ditolak di Interview Industri?

Di lingkungan produksi fintech dengan jutaan catatan transaksi, perbedaan kompleksitas waktu antara O(N) dan O(N²) adalah perbedaan antara sistem yang responsif dalam milidetik atau sistem yang mengalami kelumpuhan (Time Limit Exceeded).

❌ Brute Force Nested Loop O(N²):
for i := 0; i < n; i++ {
  for j := i + 1; j < n; j++ { ... }
} // N = 10.000 → 100.000.000 iterasi! (TLE)
✅ Single-Pass Hash Map O(N):
seen := make(map[int]bool)
for _, num := range nums {
  // Lookup O(1) amortized → N iterasi saja!
} // N = 10.000 → hanya 10.000 operasi (< 1 ms)
🎯 Modul L2 • Pola Pencarian Target Complement Complement Pattern

Bagaimana Mengubah Masalah Pasangan Menjadi Pencarian O(1)?

Alih-alih mencari pasangan secara membabi-buta dengan membandingkan tiap angka satu per satu, gunakan identitas matematika dasar:

// Relasi Matematika:
A + B = Target  ↔  B = Target - A  (di mana B adalah "Komplemen")
// Alur Eksekusi Single-Pass:
1. Saat berada di angka A, hitung komplemen yang kita butuhkan: target - A
2. Cek ke Hash Map: "Apakah komplemen ini sudah pernah kita temui sebelumnya?"
3. Jika YA → Pasangan ditemukan! Kembalikan hasil langsung.
4. Jika BELUM → Simpan A ke dalam Hash Map, lalu lanjutkan ke elemen berikutnya.

🛡️ Modul S1 • Mengapa Disable Button di Frontend Tidak Cukup? API Idempotency

Anomali Timeout Jaringan & Retry Otomatis

Di dunia nyata, request HTTP transfer uang bisa sukses didebit di database, tetapi koneksi putus saat mengirim respons balik ke aplikasi mobile nasabah. Aplikasi mobile yang timeout akan secara otomatis me-retry request kedua.

❌ Tanpa Idempotency Key:

Server menganggap retry kedua sebagai transaksi transfer baru. Saldo nasabah terpotong dua kali untuk pesanan yang sama (Double Spending / Overbilling)!

✅ Dengan Idempotency Key (UUID):

Server memeriksa status key. Jika sudah pernah sukses diproses, kembalikan response tersimpan tanpa memotong saldo ulang (Safe Replay • HTTP 200 OK).

📒 Modul S2 • Double-Entry Bookkeeping & Audit Trail Debit = Kredit

Mengapa Tabel Saldo Sederhana Dilarang di Sistem Finansial?

Menyimpan saldo hanya sebagai satu kolom angka (UPDATE accounts SET balance = balance - 100) tidak dapat diaudit ketika terjadi perbedaan saldo. Sistem perbankan wajib menggunakan Double-Entry Ledger:

// Hukum Dasar Pembukuan Akuntansi:
Σ Total Debit ≡ Σ Total Kredit  (Jumlah mutasi selalu NET ZERO)
// Contoh Transfer $100 dari Alice ke Bob dalam 1 Transaksi Database:
Entry 1: Debit Account Alice -$100 (Uang keluar dari pengirim)
Entry 2: Kredit Account Bob +$100 (Uang masuk ke penerima)
// Selisih = (-100) + (+100) = 0 → Rekonsiliasi Akurat 100%
🔥 Modul S3 • Perlindungan Flash Sale & Thundering Herd Token Bucket Rate Limiter

Mengapa Database Pool Bisa Tumbang Saat Flash Sale?

Saat ribuan pengguna menekan tombol "Beli Sekarang" pada detik ke-0 flash sale, jika semua request diteruskan langsung ke PostgreSQL, connection pool database akan habis (exhausted) dan latensi melonjak dari 5ms menjadi 30 detik.

Solusi Pertahanan Gerbang (Token Bucket di Reverse Proxy / Gateway):

Batasi throughput (misal 40 RPS). Request yang melebihi kapasitas gerbang langsung dijawab dengan HTTP 429 Too Many Requests dalam hitungan mikrodetik tanpa menyentuh koneksi database sama sekali!

Topik: Data Integrity

Mengapa tipe data float64 dilarang keras untuk menyimpan saldo uang di sistem backend?

Poin Jawaban Verbal: Representasi biner IEEE-754 memiliki kelemahan presisi (misal: 0.1 + 0.2 = 0.30000000000000004). Di sistem fintech, selalu gunakan int64 dalam satuan sen terkecil (contoh: Rp 50.000 disimpan sebagai 5000000 sen) atau tipe data NUMERIC(18, 4) di database SQL.
Topik: Database Concurrency

Kapan kita harus memilih Pessimistic Locking dibanding Optimistic Locking?

Poin Jawaban Verbal: Gunakan Pessimistic Locking (SELECT FOR UPDATE) ketika frekuensi konflik transaksi sangat tinggi pada entitas yang sama (seperti dompet akun hot-wallet atau flash sale) agar tidak terjadi retry loop yang membebani CPU. Gunakan Optimistic Locking (kolom version) ketika transaksi sangat jarang bertabrakan (misal: update profil nama user).
Topik: Distributed Systems

Apa yang harus dilakukan jika request kedua masuk saat request pertama masih berstatus PROCESSING?

Poin Jawaban Verbal: Kembalikan HTTP 409 Conflict dengan header Retry-After. Ini menandakan operasi sedang berlangsung sehingga klien tidak boleh melakukan retry acak yang bisa menyebabkan race hazard atau dual execution.
Topik: Go Language Idioms

Mengapa Go memilih explicit error checking (if err != nil) daripada try-catch exception?

Poin Jawaban Verbal: Error di Go diperlakukan sebagai first-class values biasa. Ini memaksa perekayasa perangkat lunak untuk secara sadar menangani setiap kemungkinan kegagalan di titik terjadinya (fallibility transparency) tanpa alur program tersembunyi yang bisa memicu panic di tengah transaksi keuangan.
