Bootcamp Fase 1 • Fondasi Bahasa Go & RDBMS

Belajar Golang Dasar, Pointers, Goroutines, hingga Konsep Concurrent & RDBMS

Go (Golang) Railway RDBMS / SQL

Belajar Golang dasar mulai dari instalasi, memahami variable, const dan tipe data pada GO programming, hingga konsep concurrent bahasa GO dan eksplorasi relational database (RDBMS).

Modul 1 • Function & Packages Syntax & Scope

Organisasi Package, Exported Identifier & Error Return

Go menggunakan kapitalisasi huruf untuk menentukan visibility: huruf depan kapital (CalculateFee) bersifat publik (exported), sedangkan huruf kecil bersifat privat. Fungsi mendukung multiple return value untuk mengembalikan error secara eksplisit.

Modul 2 • Pointers, Struct & Methods Memory Reference

Pointer Receiver vs Value Receiver & Interface Duck Typing

Pahami kapan menggunakan pointer (*User) agar mutasi state tidak membuat salinan memori baru. Interface di Go diimplementasikan secara implisit tanpa keyword implements, memudahkan pembuatan unit test mock.

Modul 3 • Go-Routines & Channel Concurrent CSP

Pengenalan Konsep Concurrent, Buffered Channel, Select & Mutex

Eksekusi fungsi di thread ringan goroutine (go worker()). Komunikasikan data antar-goroutine melalui buffered channel, multiplexing dengan select, dan lindungi shared memory dengan sync.Mutex.

Normalisasi Relasional, Advanced Query & Transaksi ACID

Mengeksplorasi skema database relasional (RDBMS) menggunakan DDL (CREATE TABLE, ALTER) dan DML (SELECT, INSERT). Kuasai integritas transaksi ACID dan Row-Level Locking (FOR UPDATE).

⚖️ Code Comparison: Anti-Pattern Pemula vs Standar Produksi Fintech

Money Precision
❌ Anti-Pattern (Floating-Point Float64) BAHAYA AUDIT 
// SALAH: 0.1 + 0.2 != 0.3 di biner IEEE-754
var balance float64 = 10000.50
fee := balance * 0.11 // PPN 11%
// Menghasilkan selisih sen mikroskopis
// yang menumpuk jadi audit leakage!

Floating-point memiliki pembulatan representasi biner. Dalam 1 juta transaksi, selisih 0.0000001 sen akan menimbulkan selisih pembukuan neraca jutaan rupiah.

✅ Best Practice (Pure Integer Math int64 Cents) FINTECH STANDARD 
// BENAR: Seluruh nominal dalam satuan sen (int64)
var balanceCents int64 = 1000050 // Rp 10.000,50
// Rumus integer: (cents * rate) / 100
feeCents := (balanceCents * 11) / 100
// Presisi 100% konsisten tanpa drift

Sistem perbankan dan core payment mutlak menggunakan integer cents di aplikasi dan tipe BIGINT atau NUMERIC di database.

Topik: Pointers & Receivers

Kapan wajib menggunakan Pointer Receiver (func (w *Wallet)) dibanding Value Receiver?

Kunci Jawaban: Wajib pointer receiver jika method perlu mengubah field struct (mutasi state), atau jika struct berukuran besar sehingga pembuatan salinan memori tidak efisien. Jika menggunakan Mutex di dalam struct, pointer receiver mutlak agar mutex tidak tersalin.
Topik: Concurrency Channels

Apa perbedaan fatal antara Unbuffered Channel vs Buffered Channel?

Kunci Jawaban: Unbuffered channel memblokir pengirim sampai ada penerima yang siap (synchronous rendezvous). Jika tidak ada penerima, pengirim terkunci (deadlock hazard). Buffered channel memiliki kapasitas penampung, pengirim hanya memblokir jika buffer penuh.
Topik: Data Types & Invariants

Mengapa nilai uang mutlak TIDAK BOLEH disimpan sebagai float64?

Kunci Jawaban: Representasi biner IEEE-754 floating point memiliki ketidakpresisian pecahan (misal: 0.1 + 0.2 = 0.30000000000000004). Selalu simpan nominal uang dalam integer sen (int64) atau tipe SQL NUMERIC(18, 4).
Topik: RDBMS Locking

Apa fungsi SELECT ... FOR UPDATE pada database relasional?

Kunci Jawaban: Menerapkan Row-Level Lock eksklusif pada baris yang dibaca hingga transaksi selesai (COMMIT/ROLLBACK). Mencegah transaksi lain mengubah data saldo secara bersamaan, sehingga mencegah race condition overdraft.

⚖️ Code Comparison: Anti-Pattern Goroutine vs Bounded Worker Pool

Goroutine Safety
❌ Anti-Pattern (Unbounded Goroutines) OUT OF MEMORY 
// BAHAYA: Setiap request spawn goroutine baru
func HandlePayment(w http.ResponseWriter, r *http.Request) {
    go func() {
        // Jika datang 50.000 RPS,
        // akan ada 50.000 goroutine aktif!
        db.ExecutePayment(...)
    }()
}

Memicu lonjakan konsumsi memori dan menghabiskan connection pool database (DB Pool Exhaustion 100/100).

✅ Best Practice (Bounded Worker Pool & Queue) PRODUCTION READY 
// BENAR: Jumlah worker dibatasi (misal: 20 worker)
tasks := make(chan PaymentTask, 500)
for w := 0; w < 20; w++ {
    go worker(ctx, tasks)
}
// Request baru masuk ke buffer channel
// Jika antrean penuh, kembalikan HTTP 429!

Beban database stabil dan terkontrol. Backpressure diterapkan secara elegan menggunakan buffered channel.

Topik: Concurrency Patterns

Kapan arsitektur Fan-Out / Fan-In lebih menguntungkan dibanding pemanggilan serial?

Kunci Jawaban: Saat satu request butuh data dari beberapa upstream independen (misal: cek skor kredit, saldo rekening, dan validasi KYC). Fan-out mengeksekusi semua panggilan secara paralel, dan Fan-in menggabungkan hasilnya ke 1 channel, memangkas latensi dari penjumlahan menjadi latensi panggilan terlambat.
Topik: Context Propagation

Mengapa parameter context.Context wajib dioper sebagai argumen pertama fungsi?

Kunci Jawaban: Merupakan konvensi standar Go idiom agar sinyal timeout dan pembatalan (cancellation) dari klien HTTP dapat dipropagasikan ke layer database dan downstream service secara seragam. Jangan pernah menyimpan context di dalam struct!
Topik: Performance Testing k6

Apa perbedaan metrik p95 vs p99 saat menguji ketahanan endpoint pembayaran?

Kunci Jawaban: Rata-rata (average) menipu karena outlier tertutupi. p95 menunjukkan batas latensi 95% pengguna tercepat. Sedangkan p99 menunjukkan 1% transaksi paling lambat (biasanya akibat garbage collection pause, lock contention, atau cold cache). Di fintech, SLA ditentukan oleh p99.
Topik: Database Migrations

Mengapa setiap migrasi wajib memiliki pasangan file up.sql dan down.sql?

Kunci Jawaban: Agar sistem CI/CD deployment memiliki kemampuan rollback otomatis (down.sql) secara aman jika rilis versi baru mengalami kegagalan, tanpa merusak konsistensi tabel yang sudah ada.

⚖️ Code Comparison: Blocking DDL vs Zero-Downtime Concurrent Migration

Zero-Downtime DB
❌ Anti-Pattern (Blocking Table Lock) OUTAGE SEV-1 
-- BAHAYA: Mengunci tabel transactions
CREATE INDEX idx_user ON transactions(user_id);
-- Pada tabel 20 juta baris, DDL ini butuh 8 menit.
-- Semua transaksi write terblokir!
-- Gateway timeout 504 di jam sibuk!

`CREATE INDEX` standar di PostgreSQL memperoleh *ShareLock*, menahan seluruh operasi `INSERT` dan `UPDATE` transaksi.

✅ Best Practice (Concurrent Non-Blocking) FINTECH GRADE 
-- BENAR: Non-blocking zero-downtime
CREATE INDEX CONCURRENTLY idx_user 
ON transactions(user_id, created_at);
-- Berjalan di background tanpa lock tabel
-- Transaksi pembayaran tetap jalan 100%!

Klausa `CONCURRENTLY` membangun indeks tanpa table lock, menjaga SLA ketersediaan sistem pembayaran 99.99%.

Klik untuk membuka kunci jawaban
Topik: gRPC vs REST JSON

Mengapa komunikasi internal antar-microservice lebih disukai menggunakan gRPC dibanding REST JSON?

Kunci Jawaban: gRPC menggunakan transmisi biner Protobuf di atas HTTP/2 multiplexing (1 koneksi TCP untuk banyak request serentak). Tidak ada overhead parsing teks JSON string, ukuran payload 5x lebih kecil, dan mendukung streaming dua arah (bi-directional).
Topik: Cache Stampede (Thundering Herd)

Apa itu fenomena Cache Stampede dan bagaimana cara mitigasinya di Go?

Kunci Jawaban: Terjadi saat hot key cache kedaluwarsa di jam sibuk, ratusan goroutine serentak menembak database untuk data yang sama. Di Go dimitigasi dengan golang.org/x/sync/singleflight yang menduplikasi hasil request pertama ke seluruh goroutine yang sedang menunggu.
Topik: Docker Multi-Stage

Mengapa Dockerfile untuk aplikasi Go wajib menggunakan Multi-Stage Build?

Kunci Jawaban: Stage builder menggunakan image besar dengan Go compiler. Stage final hanya menyalin binary hasil kompilasi ke base image minimal (scratch atau alpine), memangkas ukuran image dari ~800MB menjadi < 20MB dan meminimalkan celah keamanan OS.
Topik: Real-Time SSE vs WebSockets

Kapan Server-Sent Events (SSE) lebih tepat digunakan dibanding WebSockets?

Kunci Jawaban: SSE tepat digunakan saat komunikasi data hanya berjalan satu arah dari server ke klien (unidirectional streaming, misal: feed event transaksi atau status SSE). SSE berjalan di atas HTTP standar tanpa overhead protokol khusus dan memiliki fitur auto-reconnect bawaan di browser.
